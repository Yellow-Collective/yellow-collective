## Findings

- **GET requests can write.** `getPublicRoundBySlug` finalizes winners when ended (`data/rounds.ts:2078-2082`). Voting-power GET also resolves a missing snapshot (`pages/api/rounds/[slug]/voting-power.ts:39-44`), persisting its block (`data/rounds.ts:2268-2277`). All database helpers invoke `ensureTables`, containing DDL and backfills, including null Comic Strips caps becoming 25 (`data/rounds.ts:561-565`), submission-image backfills (`579-583`), and end-date changes (`642-645`). Strict read-only inspection should use direct read-only SQL rather than these application helpers.
- **Eligibility is historical delegated power.** `getVotes(address)` at the snapshot block determines eligibility (`utils/rounds/getCollectiveNounVotingPower.ts:26-29`). Zero delegated votes means zero allocation; positive power plus configured base allocation applies under `base_plus_voting_power` (`utils/rounds/getRoundVotingPower.ts:11-27`). Ownership alone is insufficient.
- **Snapshot selection and changes.** Custom timestamp or voting start selects the latest block at or before that timestamp (`utils/rounds/voting-snapshot.ts:14-19`; `getCollectiveNounVotingPower.ts:44-77`). Resolution is locked and persisted (`data/rounds.ts:2216-2281`). Effective snapshot timing cannot change after block resolution (`3034-3051`). Per-entry cap cannot change after voting begins (`3024-3032`), but strategy, base allocation, deadlines, and winner count remain editable (`3055-3082`). This module contains no configuration-change audit history.
- **Authentication.** Signed requests bind wallet, chain, action, method/path, domain/URI, and payload hash to a five-minute nonce (`utils/signature-auth-server.ts:17`, `398-433`). Nonce consumption is atomic before normal vote processing.
- **Normal enforcement.** Votes require active published round, voting-open state, approved nondeleted target, positive integer count, no duplicate submission IDs, cumulative cap, and remaining wallet capacity. Wallet advisory locks serialize changes (`pages/api/rounds/[slug]/vote.ts:34-66`; `data/rounds.ts:3766-3844`; `utils/rounds/validateRoundVote.ts:23-65`). Self-vote prohibition compares wallet addresses only (`data/rounds.ts:3745-3750`, `3797-3802`), not beneficial control.
- **Vote chronology limits.** Normal votes increment existing rows while retaining original `created_at` and updating `updated_at` (`data/rounds.ts:3846-3860`). There is no separate log of each normal increment, so a current row cannot reconstruct every earlier allocation.
- **Admin exceptions and audit.** Admin mutation endpoints require admin authorization and `rounds` permission (`pages/api/admin/rounds/[id]/votes/[voteId].ts:49-86`; `utils/admin-api.ts:34-65`). Updates/deletions lock the wallet and atomically record administrator, before/after state, and reason (`data/rounds.ts:2510-2664`). Admin updates do not enforce historical eligibility, self-vote prohibition, per-entry cap, total capacity, voting-open state, or target approval. Anomalous rows therefore require reconciliation with admin history before attributing them to voter activity. The audit table covers application admin update/delete only, not insertions, direct SQL, normal increments, or configuration edits (`438-448`, `2468-2507`).
- **Moderation effects.** Deleting vote rows frees allocation capacity while voting is open (`data/rounds.ts:2648-2650`, `3695-3711`). Hiding, rejecting, or soft-deleting a submission retains its vote rows and their capacity usage (`3633-3688`).
- **Public coverage.** Public vote activity excludes deleted submissions but includes non-approved submissions (`data/rounds.ts:2293-2307`). Public submission listing includes approved entries or frozen winners only (`2130-2132`). It is not a complete raw database ledger.
- **Tie breaking.** Winner order is total votes descending, then submission creation time descending: newer entry wins a vote tie (`data/rounds.ts:2167-2181`). Equal counts and equal creation timestamps lack an explicit tertiary key.
- **Frozen winners.** Any existing winner row causes finalization to return without recalculating (`data/rounds.ts:2158-2164`). Corrections or disqualifications do not automatically refresh stored winners. A rejected/hidden frozen winner remains eligible for public display through the winner join (`2132`). No alternate `round_winners` update or delete path was found in deployed source. Authorized moderation after finalization requires separate winner reconciliation.

## Published rule evidence and limits

Displayed source says “You cannot vote for your own entry” (`pages/rounds/[slug].tsx:797`). Searching deployed `data/`, `pages/`, and `utils/` found no Comic Strips transfer, loan, multiple-wallet, Sybil, or vote-manipulation disqualification rule. This does not establish that external published terms or production round content contained no additional rule; those are outside this source-only review.

## Dirty-work distinction

Local `data/rounds.ts` adds aggregation before entry-cap comparison; local `pages/rounds/[slug].tsx` adds cap-reached UI and self-vote notice styling. These are absent from both compared deployed versions. Deployed `validateRoundVote.ts:29-30` already rejects duplicate IDs, so the dirty aggregation patch is not proof of an exploitable deployed duplicate-allocation route. All existing dirty and untracked work was preserved.
